# V9 → V10 操作系统编写指南

## 读前须知

这不是一份"先读后做"的理论文档。这是一份**积木搭建说明书**——每一层告诉你可以开始搭下一个积木的信号是什么，以及这个积木对应的 Linux 概念是什么。

**原则：基础设施优先。插件永远排在底座后面。**

## 三、积木搭建顺序（按这个来，一次一块）

### 🧱 积木 1：上下文窗口管理 ← **现在就做**

**你需要的 Linux 概念：** `mm/memory`（内存管理）

**要解决的问题：**
- LLM 上下文窗口有限（DeepSeek 64K token ≈ 中文约 3 万字）
- 当前行为：所有历史轮次 + 工具结果全往里塞
- 20 轮对话后窗口满 → LLM 静默截断最前面的内容 → Agent "突然失忆"
- 没有任何预警或降级机制

**你要造的：**
```
LLMBridge 层加一个 ContextWindowManager:
  ├─ 每轮执行前计算当前窗口的 token 估计值
  ├─ 如果接近上限 (90%) → 启动驱逐策略
  │   ├─ P0 社交轮次优先丢弃（寒暄不重要）
  │   ├─ 大工具结果 → 摘要替代原文
  │   └─ 历史轮次 → 保留最近 N 轮，旧的扔
  ├─ 如果已达上限 → 通知内核（Event: CONTEXT_WINDOW_FULL）
  │   → DataPolicy.verbosity_budget 收紧（简短回复省 token）
  └─ 可观测：告诉外部"窗口用了多少"（为后面的 /proc 做准备）
```

**动手信号：** 现在。你今天跑 CLI 就会撞到。
**依赖：** 无。纯 LLMBridge 层改动。
**改动量：** ~150 行，1-2 文件。
**对应 Linux 版本：** Linux 0.12 (1992) — 引入虚拟内存管理

---

### 🧱 积木 2：优雅关机 ← **跟积木 1 一起做**

**你需要的 Linux 概念：** `init/systemd` + `kernel/signal`

**要解决的问题：**
- Ctrl+C 后 telemetry 缓冲区丢失（后台 writer 还在 asyncio.Queue 里）
- 没有 flush → 最后一轮的 (s,a,r) 数据永久丢失
- 远程场景下没有"你现在可以安全关机了"的确认

**你要造的：**
```
app.py 加 signal handler (SIGINT/SIGTERM):
  ├─ 捕获 Ctrl+C
  ├─ 停止接收新输入（设置 stopping flag）
  ├─ 等待当前 in-flight 操作完成（最多 5 秒）
  ├─ 刷新 telemetry 缓冲区 → 写入磁盘
  ├─ 关闭所有总线连接
  └─ 打印 "Agent 已安全停止" → 退出

主循环:
  while not stopping:
      try: step()
      except: graceful_shutdown()
```

**动手信号：** 每次 Ctrl+C 都丢数据。
**依赖：** 无。
**改动量：** ~60 行，2 文件。
**对应 Linux 版本：** System V init (1983) — 基本的启动/停止

---

### 🧱 积木 3：可观测性 (`/proc`)

**你需要的 Linux 概念：** `fs/proc` + `sysfs`

**要解决的问题：**
- Agent 跑着跑着行为不对，你只能看日志猜
- 不知道当前 trust 是多少、context_depth 是多少、哪个 gate 触发了
- 不知道 PluginRegistry 里挂了哪些插件、哪些加载失败
- 不知道 token 用量、队列深度、LLM 延迟

**你要造的：**
```
一个 inspect API（CLI 命令或 HTTP 端点）:
  /status    → {"trust": 0.37, "e_t": 0.0, "mode": "NORMAL", "round": 15, ...}
  /plugins   → {"tool": ["write_file", ...], "prompt": ["core_prompts"], ...}
  /metrics   → {"llm_latency_ms": [450, 380, ...], "token_used": 3200, ...}
  /trace     → 最近 N 轮的 DecisionTrace

实现: Harness 加一个 dump_state() 方法 → CLI 命令 `python v9_cli.py --inspect`
```

**动手信号：** 出 bug 时你不知道 Agent 内部什么状态。
**依赖：** 积木 1（窗口管理提供了 token metrics）
**改动量：** ~100 行。
**对应 Linux 版本：** Linux 0.98 (1992) — 引入 /proc 文件系统

---

### 🧱 积木 4：Token 预算控制

**你需要的 Linux 概念：** `kernel/cgroup`（资源控制组）

**要解决的问题：**
- 一个工具调用返回了 10KB 的搜索结果 → 把上下文窗口塞爆
- Agent 没有"这个月只能用 100K token"的概念
- 不能给不同的用途（Planning vs Synthesis vs Critic）分配不同的 token 预算

**你要造的：**
```
TokenBudget:
  ├─ 总预算: 每会话/每日 token 上限
  ├─ 按用途分配: Planning 30%, Synthesis 50%, Critic 20%
  ├─ 预警: 剩余 20% → DataPolicy.verbosity_budget → 0.3
  ├─ 超限: emit TOKEN_BUDGET_EXCEEDED → kernel → WAIT
  └─ 可观测: /metrics 暴露用量

集成: 在 LLMBridge._translate_policy() 里查询剩余预算
     → max_tokens = min(policy.max_tokens, budget.remaining)
```

**动手信号：** 跑一天下来 token 账单吓人，或者工具返回撑爆窗口。
**依赖：** 积木 1（窗口管理）+ 积木 3（可观测）
**改动量：** ~100 行。
**对应 Linux 版本：** Linux 2.6.24 (2008) — cgroup 合并入主线

---

### 🧱 积木 5：Agent 沙箱

**你需要的 Linux 概念：** Docker (`namespace` + `cgroup`)

**要解决的问题：**
- MCP 工具是别人的代码。它崩了不能炸毁内核。
- 一个工具不能读其他工具的输出。
- 一个工具不能访问文件系统任何位置（即使在沙盒目录内）
- 工具执行应该有时间限制和内存限制

**你要造的：**
```
ToolSandbox:
  ├─ subprocess 隔离: 每个工具调用 fork 子进程
  ├─ 文件系统限制: chroot 或目录白名单
  ├─ 超时: 工具 30 秒不返回 → kill
  ├─ 内存限制: 512MB 上限（可选）
  └─ 异常隔离: 子进程 segfault → 只影响这一轮，内核继续

集成: ToolBridge.execute() 里加 sandbox wrapper
     不是替代 _ToolWrapper，是包在它外面
```

**动手信号：** 你接入了第一个外部 MCP 工具。
**依赖：** 积木 4（资源控制是沙箱的前提）
**改动量：** ~200 行。
**对应版本：** Docker 1.0 (2014)

---

### 🧱 积木 6：多 Agent 调度器

**你需要的 Linux 概念：** `kernel/sched` (CFS — 完全公平调度器)

**要解决的问题：**
- 3 个 Agent 同时跑：一个在思考、一个在调工具、一个在等 LLM 返回
- 谁先用 LLM？公平分配：round-robin 还是按优先级？
- 一个 Agent 卡住了不能阻塞所有其他 Agent

**你要造的：**
```
AgentScheduler:
  ├─ 多个 Agent 实例共享一个 LLM 连接池
  ├─ 调度策略: round-robin（公平）或 priority-based（关键 Agent 优先）
  ├─ 抢占: LLM 调用超过 30 秒 → 标记为 blocked → 调度下一个
  └─ 隔离: 每个 Agent 有自己的 KernelState、自己的上下文窗口

注意: 这是 V9 架构的"分叉点"——当前 kernel_step 是单 Agent 的纯函数。
     多 Agent 意味着需要多个 KernelState 实例并行演化。
```

**动手信号：** 你需要同时运行 2+ 个 Agent 实例。
**依赖：** 积木 4（资源控制）+ 积木 5（沙箱隔离）
**改动量：** ~300 行 + 架构调整。
**对应版本：** Linux 2.6.23 (2007) — CFS 并入主线

## 五、当你不确定优先级时

按这个顺序问自己：

1. **我今天跑 CLI 会撞到吗？** → 是 → 立刻做
2. **下一个积木依赖它吗？** → 是 → 在做依赖它的积木之前做
3. **它是插件层的事吗？** → 是 → 底座完工前不碰
4. **能用 100 行以内解决吗？** → 是 → 直接做，不讨论

**永远不做的事：**
- 为了未来的性能优化现在（YAGNI）
- 为了"完整性"去填补没有实际痛点的缺口
- 在底座没搭好时往上层堆插件

## 六、Linux 演进史作为你的路线图参考

```
1991: Linux 0.01 — 裸内核，单进程                  → V9.0
1992: Linux 0.12 — 虚拟内存，多进程雏形             → 积木 1+2
1992: Linux 0.98 — /proc 文件系统                  → 积木 3
1994: Linux 1.0 — 网络栈，稳定 API                  → V9.2 封版
2001: Linux 2.4 — 64GB 内存支持，大规模扩展          → (你在这里)
2007: Linux 2.6.23 — CFS 调度器                     → 积木 6
2008: Linux 2.6.24 — cgroup                         → 积木 4
2014: Docker 1.0 — 容器化                           → 积木 5
2024: Linux 6.x — eBPF，Rust 支持，AI 加速           → 未来

你现在是 1994 年的 Linux 1.0 — 内核有了，API 稳定了。
下一步是 2001 年的 2.4 — 让它能承载"真正的负载"。
```

## 七、最后的诚实提醒

这份指南不是真理。它是一个人在 2026 年 6 月对 AI Agent 操作系统的理解。两件事可能会推翻它：

1. **你在搭积木 1 的时候，发现上下文窗口管理需要改动内核 ODE**——那就改。指南不是宪法。
2. **DeepSeek 把上下文窗口从 64K 扩到 1M**——窗口管理变得不那么紧急。优先级重排。

**这份指南的价值不是"对"，是"给你一个可以推翻的起点"。**
