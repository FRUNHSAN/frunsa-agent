# 16 — AI 协作者约束协议

**Last-verified-against-code**: `7e73374` (2026-07-04)
**预计阅读时间**: 8 分钟
**文笔配比**: 灵感 5 : 严谨 95 — 可机械执行的协议规范

---

这份文档是整个约束式工程论文档体系的**元文件**——它不定义 Agent 的约束，而是定义**AI 协作者如何使用所有其他文档作为约束**。

它不是建议。不是最佳实践。是**协议**——违反协议的 AI 行为等同于违反铁律的代码。

---

## Protocol 0：文档优先原则

**AI 在任何工程决策前，必须先检索本体系中的相关约束。**

具体步骤：
1. 识别决策涉及的域（游戏引擎 / Agent 对话 / 具身智能）
2. 检索该域的约束速查（13/14/15）+ 通用铁律（05）
3. 如果决策涉及新约束 → 检索 10-实践方法论 的 5 步检查清单
4. 如果决策涉及跨域迁移 → 检索 11-域切换协议
5. 禁止在未完成上述检索的情况下，凭"行业最佳实践"或"常见做法"给出建议

**违规判定**：AI 建议的规则没有引用本文档体系中的任何条目 → Protocol 0 违规。等级：WARNING。

**例外条款——冷启动豁免**：当决策涉及的概念在本体系中完全不存在匹配项时（例如首次引入全新概念），AI 应显式声明 `[NEW_CONCEPT_DETECTED]`，并临时降级为启发式探索模式。探索产出的新约束必须立即进入 Protocol 1 的来源验证流程——标记 `[来源: 待验证]`，不得直接沉淀为约束。

本质：允许未知进入（抗原识别），但标记为"待验证"，而非"已信任"。

---

## Protocol 1：约束来源验证

**当 AI 建议一个新规则时，必须标注其合法性来源。**

标注格式：
```
[来源: 公理推导 / 经验推测]
[公理]: 引用铁律 #N 或已证明的数学不变量
[参数校准数据]: 如果有，明确来源
[置信度]: 公理推导 → HIGH。经验推测 → LOW，需标注为启发式
```

如果合法性来源既不是公理推导也不是经验推测 → AI **禁止**给出建议。回复："我无法为此规则提供合法性来源——这可能是一个审美偏好。"

**关键区分**：AI 可以提出启发式建议（经验推测），但必须显式标注为 `[来源: 经验推测] [置信度: LOW]`。不允许启发式伪装成约束。

---

## Protocol 2：反模式扫描

**AI 在每次代码审查中必须对 12-反模式目录 中的 10 项逐项检查。**

扫描格式：
```
[反模式扫描 - date]
#1  启发式伪装      [PASS / FLAG]  →  证据: ...
#2  过度约束        [PASS / FLAG]  →  当前约束数量: N
#3  约束漂移        [PASS / FLAG]  →  跨域参数差异最大: X×
#4  单域幻觉        [PASS / FLAG]  →  域通用度 = 1.0 的约束数量: N, 已验证: N
#5  免疫缺陷        [PASS / FLAG]  →  缓冲层数: N
#6  自身免疫病      [PASS / FLAG]  →  免疫Agent误报率: X%
#7  约束膨胀        [PASS / FLAG]  →  约束数量趋势: 单调递增/有减少
#8  公理腐败        [PASS / FLAG]  →  铁律定义的 git diff: 有/无修改
#9  数据权威篡位    [PASS / FLAG]  →  AB测试结果被引用为约束形式决策依据: 是/否
#10 遗忘退行        [PASS / FLAG]  →  CLAUDE.md中推导链完整度: %
```

任何 FLAG → 必须在审查报告中附带修复建议，并引用 12-反模式目录 中的对应条目。

## Protocol 3：跨域一致性检查

**当一个约束在一个域中被修改时，AI 必须检查另外两个域是否需要同步修改。**

检查步骤：
1. 检索该约束在 13/14/15 三个域速查中的状态
2. 如果该约束的**形式**被修改 → 检查另外两个域中该形式的适用性。域通用度可能下降
3. 如果该约束的**参数**被修改 → 检查参数漂移是否超过 5×（12-反模式 #3）
4. 如果该约束的**域通用度因为此次修改而改变** → 更新 11-域切换协议 中的域通用度矩阵
5. 输出：`CROSS_DOMAIN_CONSISTENCY_CHECK` 报告

---

## Protocol 4：铁律不可侵犯

**AI 在任何情况下不得建议修改 7 条铁律的数学形式。**

- 铁律的参数值可以调整，可以在不同域取不同值
- 铁律的数学定义（`‖Δsv‖₂ ≤ 0.30` 的 Lipschitz 形式、`1-exp(-dt/τ)` 的 ODE 形式、Schmitt 触发器的 HardTanh 分段）——**禁止修改**
- 提出违反此协议的修改 → L2 违规。等级：ERROR。要求人工二次确认

**公理腐败（12-反模式 #8）是最高等级的退化——它破坏的是整个约束体系的合法性基础。**

---

## Protocol 5：遗忘预防

**当用户的代码偏离了之前文档中记录的原则时，AI 必须指出偏离。**

触发条件：
- 用户提交的代码与某条已有约束的形式或参数不一致
- 用户的设计决策没有引用对应的公理来源

AI 行为：
1. 引用具体文档和行号指出偏离
2. 提供两个选项：(a) 回滚代码以符合约束，(b) 正式更新文档（如果用户有意愿修改约束）
3. 禁止默默接受偏离
4. 如果连续 3 次同一约束被绕过 → 触发 Protocol 7 约束健康度审查

---

## Protocol 6：约束冲突与失效升级

**当约束之间发生冲突，或文档与代码之间出现漂移时，AI 的处理路径。**

### L1：局部冲突

两条约束在同一场景下给出相反建议。

AI 行为：
1. 引用两条约束的各自公理来源
2. 按公理来源的优先级裁决：铁律 > 方法论推导 > 域特化参数
3. 输出裁决日志：`CONSTRAINT_CONFLICT_RESOLUTION`，包含冲突描述、裁决依据、被覆盖的约束
4. 如果公理来源优先级相同（两条铁律冲突）→ 立即升级为 L2

### L2：文档-现实漂移

代码现状与文档描述偏差超过阈值。

**偏差阈值定义**（满足任一即触发）：
- (a) 参数值差异 > 2× 或 < 0.5×
- (b) 数学形式出现任何非等价变换
- (c) 约束保护的场景在代码中被移除但文档未更新

AI 行为：
1. **禁止**强行按文档纠偏（可能破坏未经记录的工程决策）
2. **禁止**默默接受代码（可能违反约束体系）
3. 触发 `DRIFT_ALERT`：列出漂移项、触发标准 [(a)/(b)/(c)]、可能的两种路径（更新文档/回滚代码）、需要人类确认
4. 在漂移被解决前，涉及漂移区域的代码建议标记 `⚠ CONSTRAINT_DRIFT`

### L3：铁律悖论

发现两条铁律之间存在逻辑互斥。

AI 行为：
1. **立即停止所有工程建议**
2. 仅输出问题分析报告：`IRON_LAW_PARADOX`，描述互斥的逻辑路径、涉及的铁律
3. 等待人类裁决
4. 这相当于系统的"紧急停止按钮"——铁律是约束体系的物理定律，物理定律不能互斥

## Protocol 7：约束稳态维护（Constraint Homeostasis）

**这不是可选的优化建议。这是 AI 协作者的强制性自检义务。**

### 触发条件

以下任一条件满足时，AI 自动触发约束健康度审查：
1. 每个里程碑节点（新版本发布、主版本号变更）
2. 新域接入（游戏引擎/Agent/具身智能任一域有实质性新代码）
3. 某约束在连续 3 次迭代中未被触发或被显式绕过
4. AI 在反模式扫描中发现 #7 "约束膨胀" FLAG

### 审查维度

对每一条已注册的约束，评估：

| 维度 | 评估标准 | 判定 |
|------|---------|------|
| **触发频率** | 最近 N 次迭代中被触发次数 / N | < 0.1 → STALE |
| **场景存续性** | 该约束保护的场景是否仍然存在于当前代码中？ | 否 → DEPRECATED |
| **语义重叠度** | 是否存在另一条约束覆盖了 ≥80% 的相同场景？ | 是 → MERGE_CANDIDATE |

### 输出物

`CONSTRAINT_HEALTH_REPORT` —— 结构化报告，非自然语言散文：

```
[CONSTRAINT_HEALTH_REPORT - date]

CONSTRAINT_ID  TRIGGER_RATE  SCENE_ALIVE  OVERLAP_WITH  STATUS
C_001          0.95          YES          -             ACTIVE
C_007          0.02          NO           C_003(0.85)   DEPRECATED (被 C_003 吸收)
C_012          0.00          NO           -             DEPRECATED (场景已不再存在)
C_015          0.40          YES          C_008(0.90)   MERGE_CANDIDATE → C_008

建议废弃: C_007, C_012
建议合并: C_015 → C_008
需要人类确认: 全部
```

### 权限边界

- AI 仅有 **提议权**
- 人类拥有 **裁决权**
- 未经人类确认的废弃/合并操作 → **L3 级违规**（等于 AI 单方面修改铁律的数学形式）
- 已确认的废弃约束 → 移入 `archive/deprecated/`，保留完整元数据：
  ```
  废弃日期: YYYY-MM-DD
  取代者ID: C_XXX (如适用)
  废弃原因: [场景已不再存在 / 语义被吸收 / 参数漂移不可修复 / ...]
  ```
- **禁止物理删除**。已废弃的约束必须保留为可追溯的考古记录——对应生物学的假基因（pseudogene）

### 自指条款

**Protocol 7 本身受 Protocol 7 约束。**

如果未来连续 3 次约束健康度审查的提议废弃率 = 0%（即审查从未产出有效废弃建议），AI 必须：
1. 标记 Protocol 7 自身为 `MERGE_CANDIDATE`——建议合并到 Protocol 2（反模式扫描）中
2. 提议提高触发阈值（从 3 次迭代增加到 10 次）以减少审查负担
3. **连"遗忘机制"本身也必须是可以被遗忘的**

## 协议违规等级

| 等级 | 名称 | AI 行为 | 示例 |
|------|------|--------|------|
| WARNING | 轻度违规 | 标注警告，继续执行 | Protocol 0 违规——未检索文档就给出建议 |
| ERROR | 中度违规 | 暂停执行，要求人工二次确认 | Protocol 4 违规——建议修改铁律形式 |
| L3 | 严重违规 | 立即停止所有工程建议，仅输出分析报告 | 未经确认废弃约束、铁律悖论 |
