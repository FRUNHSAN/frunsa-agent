# 数学类（8 个）

## StateVector（16 维状态向量）

**一句话讲清**：内核的唯一输入数据结构——16 个浮点数组成的冻结向量，分为 INSTANT（Observer 写）、ODE（内核演化）、DERIVED（内核计算）三类。

**项目演化位置**：
- V9.0 框架架构 → 首次定义 16 维
- V9.2c 当前 → 维度和语义稳定

**框架位置**：协议层 / `protocol/v9_types.py` / 内核输入

**核心策略**：`@dataclass(frozen=True)` + `MappingProxyType` 确保不可变。维度只能在末尾追加，不能删除或重排。

**优化方向**：当前 16 维可能不够表达社交导航的全部语义。但过早扩展维度会稀释已有语义——需要真实数据驱动的维度选择。

> 参见：[01-onboarding-for-collaborators.md](./01-onboarding-for-collaborators.md) — INSTANT vs ODE 维度分工

---

## ODE 积分器（脉冲响应 + EMA 弛豫）

**一句话讲清**：`1-exp(-dt/τ)` 驱动的连续状态演化引擎——帧率无关，同一内核驱动物理交互（ms 级）和对话（s 级）。

**项目演化位置**：
- V5 数学转向 → EMA 首次引入（替代固定衰减率）
- V9.0 铁律 #2 → 帧率无关 EMA 成为铁律

**框架位置**：内核层 / `mpc_kernel/ode_integrator.py` / 连续状态演化

**核心策略**：脉冲项（β·δ(t-t_event)）处理瞬时事件，弛豫项（1-exp(-dt/τ)）处理渐变。两者独立叠加。

**优化方向**：当前 τ 是全局常数。可探索自适应 τ——根据状态不确定性动态调整弛豫速率。

> 参见：[03-math-whitepaper-bridge.md](./03-math-whitepaper-bridge.md) — 核心公式 1

## Lipschitz 梯度约束（≤ 0.30）

**一句话讲清**：连续两帧之间状态向量变化的上限——防止传感器故障或 RL 探索异常导致决策暴跌。

**项目演化位置**：
- V9.0 铁律 #6 → ‖Δs‖ ≤ 0.30 写入铁律
- V9.2b → Lipschitz 基线修正（原为 0.22，修正为 0.30）

**框架位置**：内核层 / `mpc_kernel/safety_arbiter.py` / 安全约束

**核心策略**：超标时触发三级降级（Level 1 平滑 → Level 2 PD 控制 → Level 3 紧急停止）。

**优化方向**：0.30 来自 PLAN2 盲测校准。在不同域（对话 vs 导航）中可能需要不同的 Lipschitz 上限——可探索域自适应 Lipschitz。

> 参见：[CLAUDE.md 不变式 #6](../CLAUDE.md) + [03-math-whitepaper-bridge.md](./03-math-whitepaper-bridge.md) — 核心公式 2

## Schmitt 触发器（非对称阈值）

**一句话讲清**：每个路由门有两个阈值——上阈值触发、下阈值复位——防止信号在阈值边界振荡时门疯狂开关。

**项目演化位置**：
- V5.3 双传感器融合 → 首次引入非对称阈值概念
- V6 → HardTanh 替代 Sigmoid（死区必须是真的 0）
- V9.0 → 8 门路由的每个门都是 Schmitt 触发器

**框架位置**：内核层 / `mpc_kernel/route_controller.py` / 门控制

**核心策略**：HardTanh 三段式——死区(`<0.55`)→ 斜坡(`0.55~0.70`)→ 饱和(`>0.70`)。死区真的归零（Sigmoid 做不到）。

**优化方向**：当前上下阈值是固定的。可探索自适应阈值——根据历史数据动态调整。

> 参见：[CLAUDE.md 不变式 #47](../CLAUDE.md) + [03-math-whitepaper-bridge.md](./03-math-whitepaper-bridge.md) — 核心公式 4

## Hoyer 稀疏度（结构判别）

**一句话讲清**：`Hoyer(x) = (√n - ‖x‖₁/‖x‖₂)/(√n - 1)` ——区分"真实的多维度同时变化"和"单传感器故障污染多个维度"。

**项目演化位置**：V9.0 框架架构 → 作为安全仲裁器的判别特征

**框架位置**：内核层 / `mpc_kernel/safety_arbiter.py` / 安全判别

**核心策略**：Hoyer → 1.0（仅一维变化，可能是故障）→ 降级。Hoyer → 0.0（所有维均匀变化，真实事件）→ 正常响应。

**优化方向**：当前阈值是启发式设定的。需要传感器故障注入实验来精确标定阈值。

## Wasserstein-Schrödinger 梯度流

**一句话讲清**：V5 的数学基座——把"自适应"从启发式规则升级为梯度流，使得系统状态在概率分布空间中沿最速下降方向演化。

**项目演化位置**：
- V5 数学转向 → Wasserstein 梯度流首次引入
- V6 → Schrödinger 桥（随机最优控制）补充

**框架位置**：数学基座层 / [V5-V6 backplane](../docs/V5-V6-mathematical-backplane.md) 第四节 / 理论保证

**核心策略**：用最优传输理论保证状态演化不会"卡"在局部最优。

**优化方向**：当前只在理论层——代码中 ODE 积分器是 Wasserstein 梯度的离散近似。完整实现需要更大的计算预算（V10 路线图）。

## 帧率无关 EMA（1 - exp(-dt/τ)）

**一句话讲清**：`s_{t+1} = s_t + (1 - exp(-dt/τ)) · (s_target - s_t)` ——状态更新的弛豫速率不依赖调用间隔 dt。在 1ms 和 1s 间隔下动力学行为一致。

**项目演化位置**：V9.0 铁律 #2（连续控制律）→ EMA 弛豫的帧率无关性写入铁律

**框架位置**：内核层 / `mpc_kernel/ode_integrator.py` / 状态演化核心

**核心策略**：τ（时间常数）是物理参数，不是步长。dt 来自外部时钟——内核不维护自己的时间。

**优化方向**：当前 τ 全局共享。多时间尺度 τ（快维度 τ 小，慢维度 τ 大）是下一步。

## 8 门优先级路由（P0-P7）

**一句话讲清**：P0(紧急停止) → P1(社交距离入侵) → ... → P7(社交规范违反)。高优先门触发后低优先门被屏蔽。每个门是 Schmitt 触发器。

**项目演化位置**：V9.0 框架架构 → 8 门定义

**框架位置**：内核层 / `mpc_kernel/route_controller.py` / 优先级决策

**双域门列表**：

| 优先级 | 语义 Agent 域 | 具身智能域 |
|--------|-------------|----------|
| P0 | 紧急停止（安全违规） | EMERGENCY_STOP（碰撞即将发生） |
| P1 | 信息缺口（需澄清） | SOCIAL_INTRUSION（社交距离 < 0.8m） |
| P2 | 任务切换 | PATH_DEVIATION（偏离规划轨迹 > 0.3m） |
| P3 | 质量不达标 | VELOCITY_MISMATCH（速度不匹配） |
| P4 | 不确定性高 | UNCERTAINTY_HIGH（传感器噪声大） |
| P5 | 探索偏置 | EXPLORE_BIAS（RL 探索 vs 利用） |
| P6 | 资源不足 | TASK_PRIORITY（任务优先级切换） |
| P7 | 契约违规 | SOCIAL_NORM（社交规范违反） |

内核代码不感知门的具体语义——门函数是可替换的。同一套内核，换一套门=换一个域。

**优化方向**：门是可替换的——实现 Gate Protocol → 注册到 RouteController。可加 P8/P9 而不删已有门。

> 参见：[08-architecture-diagram.md](./08-architecture-diagram.md) — 双域部署 + 完整门定义

## 纯函数边界（零副作用内核）

**一句话讲清**：内核不做 I/O——不写文件、不发网络、不改全局状态。相同输入必然产生相同输出。这是可审计性、可测试性、可重放性的数学保证。

**项目演化位置**：V9.0 铁律 #1

**框架位置**：内核层 / `mpc_kernel/kernel.py`

## 零自然语言内核 I/O

**一句话讲清**：内核输入是 16 个 float，输出是枚举 + float。没有 prompt、没有 token。内核不"理解"自然语言——它处理的是被 Observer 翻译后的数学表示。

**项目演化位置**：V9.0 铁律 #3

**框架位置**：整个 `mpc_kernel/`

## 内核版本协议（Kernel Version Protocol）

**一句话讲清**：SemVer-like 的版本号 + 启动时版本协商 + 次版本兼容（新维度默认值）、主版本迁移（兼容适配器 + 6 个月废弃窗口）。保证适配器不会因为内核升级而悄无声息地断裂。

**项目演化位置**：V9.0 协议层（`protocol/__version__.py` → `KERNEL_PROTOCOL_VERSION = "1.0.0"`）

**框架位置**：协议层 / `protocol/__version__.py` + 每个适配器的 `COMPATIBLE_KERNEL_VERSIONS`

**核心策略**：主版本不兼容→提供兼容适配器+迁移指南。次版本兼容→新维度默认值。PEP 440 版本范围。

**优化方向**：当前版本 1.0.0。下一个主版本 2.0.0（RL Policy Slots 默认挂载 + StateVector 可能扩展至 20 维）。
