## 一、RL 技术路线全景

```
RL 技术树:

                    ┌─ Value-based (Q-Learning, DQN, SAC)
                    │   核心: 学习"每个状态的价值"
                    │   适用: 离散动作空间, 样本效率低
                    │
强化学习 ───────────┼─ Policy-based (REINFORCE, PPO, TRPO)
                    │   核心: 直接学习"什么动作好"
                    │   适用: 连续动作空间, 样本效率中等
                    │
                    ├─ Model-based (MBRL, Dreamer, World Models)
                    │   核心: 先学"世界怎么运作", 再在里面做规划
                    │   适用: 需要前瞻的场景, 样本效率高
                    │
                    ├─ Imitation Learning (BC, DAgger, IRL)
                    │   核心: 看人类演示学动作
                    │   适用: 奖励函数难设计的场景
                    │
                    └─ RLHF / DPO (对齐训练)
                        核心: 用人类偏好调教模型的输出风格
                        适用: LLM 训练阶段, 让模型"更礼貌"
```

## 二、跟你项目相关的三个点（面试必问）

### 2.1 你的 policy_slots.py 就是 RL 的"策略挂载点"

```python
# V9 已有的三个策略 Protocol
BoundaryPolicy.evaluate(state) → P(A) ∈ [0,1]   # 对应 RL 的 policy π(a|s)
CostPolicy.cost(state, action, ...) → [-1,1]      # 对应 RL 的 reward R(s,a)
ValuePolicy.estimate(state, horizon) → [-1,1]     # 对应 RL 的价值函数 V(s)
```

这三个 Protocol 的设计就是 RL 的标准接口。**你现在用默认规则（HardThreshold、SchmittTrigger、ZeroPadding）填充它们。RL 训练完成后，把训练好的网络挂载到同一个槽位。** 路由链不需要改——它只看 slot 返回的值。

**面试时说：** "我的 Agent 内核预留了三个 RL 策略槽位。当前用基于规则的默认策略，但接口设计就是按 RL 的 policy/value/reward 三元组设计的。训练好的 PPO 网络可以直接挂载到 BoundaryPolicy 槽位，不改内核代码。"

### 2.2 你的 ODE 积分器就是 Model-based RL 的"内部世界模型"

```
Model-based RL:  学一个世界模型 → 在世界模型里规划 → 选择动作
V9 ODE:          ODE 积分器维护信任/误差状态 → 路由链查询状态 → 选择动作
```

你不需要从像素学世界模型——V9 的世界模型是一个 16 维的 ODE 状态向量。**这在机器人领域叫"显式状态估计"，比端到端 RL 更可控。**

**面试时说：** "端到端 RL 的问题是在机器人场景下样本效率极低——你需要成千上万次试错才能学会一个动作。我的 Agent 用一个显式的 ODE 状态向量替代隐式的神经网络世界模型。只需要几十轮交互就能收敛——因为 ODE 的结构（脉冲 + 指数松弛）本身就是对人类信任动态的先验知识。"

### 2.3 你的规则引擎 vs 模仿学习

模仿学习（BC/DAgger）：给机器人看人类怎么做 → 让它学。

你的规则引擎做的事本质上是一样的——只不过你是"手动写了 5 条规则"而不是"看了 100 个示例"。规则引擎是模仿学习的极端：**样本量 = 5 条规则，泛化 = 0，但确定性 = 100%。** 在安全关键场景（机器人握手力度），确定性比泛化重要。

**面试时说：** "模仿学习的天花板是训练数据的分布。我的规则引擎不是取代模仿学习——它是模仿学习的'安全网'。当场景在分布内、规则能覆盖，走确定性的规则引擎（零延迟、零风险）。当场景在分布外，走 LLM 或训练好的 RL 策略。这是两层防护，不是二选一。"

## 三、RL 技术路线与机器人场景的对应

| 场景 | 推荐 RL 方法 | 为什么 | V9 对应 |
|------|------------|--------|---------|
| 社交导航（让路/跟随） | BC (模仿学习) + 在线微调 | 社交规则复杂、奖励难定义 | 规则引擎做冷启动 |
| 握手/拥抱（精确力控） | Sim-to-Real + 域随机化 | 仿真里训练、真机上部署 | ODE 做状态估计 |
| 对话交互 | RLHF / DPO | LLM 对齐训练 | CorePromptBundle 换提示词 |
| 任务规划 | 分层 RL (HRL) | 高层选目标、底层执行 | 8-gate 路由链 |
| 长期陪伴（信任建模） | 基于模型的 RL | 需要预测"用户会怎么反应" | 你的 ODE 做这件事 |

## 四、面试高频 RL 问题（准备好这些答案）

### Q1: "你用过 RL 吗？"

> "我没有在项目里直接训练过 RL 模型。但我的 Agent 内核就是为 RL 准备的——它有三个策略槽位（Policy/Cost/Value），接口就是按 RL 的标准接口设计的。当前用基于规则的默认策略填充，训练好的 PPO 网络可以直接挂载。我在内核里做的一件事——用 ODE 状态向量显式建模系统状态——在 RL 领域就是一种 Model-based 方法。"

### Q2: "PPO 和 SAC 的区别是什么？选哪个？"

> "PPO 是 on-policy，样本效率低但稳定。SAC 是 off-policy，样本效率高但调参更复杂。机器人在真实环境中交互成本高——调一次动作可能撞到人——所以我会选 SAC 或其 off-policy 变体。但在这个问题上，我的选择其实是一个更根本的架构选择：能用确定性规则解决的问题（如"几点钟→Get-Date"），我不需要 RL。RL 应该只处理规则覆盖不到的场景。"

### Q3: "机器人用 RL 的最大挑战是什么？"

> "三个：1. 样本效率——真实世界不是仿真，不能重来一百万次（解法：Model-based + 仿真迁移）；2. 安全——探索过程中不能让机器人伤害人（解法：安全约束 + 规则安全网）；3. 奖励设计——社交行为的'好不好'很难量化（解法：逆强化学习 IRL 从人类演示中反推奖励函数，或者人类反馈 RLHF）。我的项目解决的是前两个——用显式状态模型提升样本效率，用安全仲裁器做硬约束。"

## 五、三句话总结（面试最后一句话）

"我的项目是一个为 RL 准备就绪的决策运行时。它有三个 RL 策略挂载点、一个显式的 ODE 状态模型做状态估计、一套规则引擎做安全兜底。RL 训练完成后可以直接部署到我的内核里——路由链不需要重写。我选择在进入 RL 之前先把系统骨架搭好，因为机器人场景下你不能靠试错搭骨架。"

## 六、如果只能记住三个东西

1. **PPO** = 最常用的 on-policy 算法，稳定但慢。记住这个名字和它是 policy gradient 就够了。
2. **Model-based RL** = 先学世界模型再规划。你说"我的 ODE 就是世界模型"——这就是你的切入点。
3. **Sim-to-Real** = 仿真训练 → 真机部署。机器人 RL 的核心挑战。你说"我的规则引擎可以在 Sim-to-Real 迁移时做安全网"。
