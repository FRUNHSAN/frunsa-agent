# V4.2 Phase 5 — 引擎层解耦 + 契约下沉

**日期:** 2026-06-07
**状态:** 计划 — 待审批
**基准:** 270 (46026ca)

---

## 背景

审计发现 3 个引擎层耦合 + 1 个根本性架构缺陷：

| 耦合 | 严重度 | 本质 |
|------|--------|------|
| 3 引擎 import `GenerationAdapter` 具体类 | 🟠 HIGH | 违反 Invariant #32——引擎应通过 Protocol 注入 |
| Planning 引擎 import + 实例化 `StubOrchestrationEngine` | 🟡 MEDIUM | 引擎间直接耦合，换 Orchestration 实现需改 Planning |
| ToolAdapter `if/elif provider` 硬分支 | ✅ 已修 | ToolFormatRegistry |

| 缺陷 | 严重度 | 本质 |
|------|--------|------|
| **引擎层零契约感知** | 🔴 CRITICAL | Planning/Orch/Critic/Tool 完全不感知 DynamicBlueprint 状态。自适应契约的所有逻辑困在 REPL 层 |

## 核心洞察：两类修复一条路径

```
解耦 = 给引擎注入 Protocol 而非具体类
契约下沉 = 给引擎注入 DynamicBlueprint，让它自主查询"合同要求我做什么？"

两者走同一条路: KernelService
  KernelService.generate(prompt)     ← 替代 GenerationAdapter 直接 import
  KernelService.enforce(key)          ← 替代蓝图零感知
  KernelService.check_tool(name)      ← 替代 REPL 手动门控
```

**这就是自适应契约的最大优势：合同成为引擎的"操作系统"。引擎不 import 任何具体类，只对 KernelService 说"我需要生成文本""我能执行这个工具吗？""当前契约允许什么？"**

## 实现步骤

### 步骤 1: 扩展 KernelService Protocol（15 分钟）

`core/contracts/kernel_service.py` — 加 3 个方法：

```python
# Phase 5 新增
async def generate(prompt, context=None, **params) -> GenerationResult: ...
def enforce(key: str) -> Any | None: ...
def check_tool(tool_name: str) -> dict: ...
```

现有的 4 个方法保留不变（event_sink, evaluate_health, decide_repair, execute_repairs）。

### 步骤 2: 让 Container 成为 KernelService 实现（20 分钟）

`core/container.py` — Container 已持有所有内核能力：
- `self.cloud_llm.generate()` → `KernelService.generate()`
- `self.bp.enforce(key)` → `KernelService.enforce(key)`
- `self.action_pipeline.check(name)` → `KernelService.check_tool(name)`

让 Container 类本身满足 KernelService Protocol（duck typing——Python Protocol 不要求显式继承）。

### 步骤 3: 引擎构造函数改为接受 KernelService（20 分钟）

3 个引擎文件的最小改动：
- `engines/planning/llm.py` — 加 `kernel: KernelService | None = None` 参数
- `engines/orchestration/llm.py` — 同上
- `engines/critic/llm.py` — 同上

引擎内部有 `kernel` 时走 kernel.generate/enforce，没有时走原始 adapter（向后兼容）。

### 步骤 4: 契约下沉——3 个引擎行为适配（15 分钟）

**PlanningEngine**: 查 `enforce("execution_autonomy")` 决定并行分支数：
```
FULL → max_parallel_branches=4
HIGH → max_parallel_branches=2
ASK_FIRST → max_parallel_branches=1 (sequential)
DISABLED → only plan, don't execute
```

**CriticEngine**: 查 `enforce("response_verbose_level")` 调整评分阈值：
```
HIGH/VERBOSE → 通过阈值 0.70 (宽松, 允许更长输出)
MEDIUM → 0.75
LOW/MINIMAL → 0.85 (严格, 必须精准)
```

**ToolEngine**: 内部调用 `check_tool()` 替代 REPL 手动门控。

### 步骤 5: 消除硬编码工厂（10 分钟）

`engines/planning/llm.py` 和 `stub.py` 的 `_default_orch_factory` 删掉硬编码 `StubOrchestrationEngine` import。
改为：如果 `orch_factory` 是 None，则设为无操作（plan only，不 orchestrate）。
实际的 orch_factory 由 Container 注入。

## 效果

```
之前:
  REPL → 读 bp.snapshot → 手动调 _apply_proposal → 手动调 check_tool
  引擎 → 零契约感知 → 硬编码行为 → import 具体类

之后:
  KernelService = 内核能力的唯一出口
  引擎 → kernel.generate() / kernel.enforce() / kernel.check_tool()
        → 契约自适应: 信任高→更多自主, 信任低→保守
  REPL → 只管用户交互, 不再手动门控
```
